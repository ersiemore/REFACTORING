# Журнал TDD и анализ покрытия

## 1. Course

**Red:** добавлены тесты создания курса, начального `enrolled == 0`, пустого названия и недопустимого `capacity`.

**Green:** реализован конструктор `Course` с валидацией входных данных и `enrolled = 0`.

**Refactor:** проверки входных данных сделаны явными и вынесены в понятные условия.

## 2. available_places

**Red:** тест нового курса ожидает количество свободных мест, равное `capacity`.

**Green:** добавлен метод `available_places()` с расчётом `capacity - enrolled`.

**Refactor:** метод оставлен простым, так как отдельной дополнительной логики ему не требуется.

## 3. enroll

**Red:** тесты описывают одну регистрацию, несколько последовательных регистраций, последнее свободное место и переполнение курса.

**Green:** `enroll()` увеличивает `enrolled`, возвращает число свободных мест и выбрасывает `ValueError`, если мест нет.

**Refactor:** проверка заполненности использует свойство `is_full`, чтобы не дублировать условие.

## 4. cancel_enrollment

**Red:** добавлены тесты отмены после регистрации, отмены при нулевом `enrolled` и восстановления свободного места.

**Green:** `cancel_enrollment()` уменьшает `enrolled` и запрещает значение ниже нуля через `ValueError`.

**Refactor:** сообщение об ошибке сделано понятным для пользователя.

## 5. is_full

**Red:** тесты проверяют пустой, частично заполненный и полностью заполненный курс.

**Green:** добавлено свойство `is_full`.

**Refactor:** свойство возвращает логическое значение напрямую из сравнения `enrolled == capacity`.

## 6. IntensiveCourse

**Red:** добавлены тесты наследования, границ `6/10/11/20` и ошибок `5/21`.

**Green:** реализован дочерний класс с `hours_per_week` и методом `workload_level()`.

**Refactor:** проверка диапазона и выбор уровня нагрузки оформлены отдельными условиями; базовая логика `Course` переиспользуется через `super()`.

## 7. Анализ покрытия

После запуска `coverage run --branch -m unittest discover` необходимо проверить:

1. общий процент покрытия строк;
2. пропущенные строки;
3. частично пройденные ветви;
4. наличие содержательных тестов для каждого реального требования;
5. повторный запуск полного набора после добавления тестов.

## Вывод для отчёта

Тесты покрывают основные обычные, граничные и ошибочные сценарии сервиса регистрации. Проверены обе ветви логики заполненности курса и обе ветви определения уровня нагрузки `IntensiveCourse`. Анализ покрытия позволяет увидеть участки, которые не выполняются во время тестов, но сам по себе высокий процент покрытия не доказывает отсутствие дефектов. Поэтому тесты должны проверять не только выполнение строк, но и ожидаемый результат через assertions.

## Ответы на вопросы для защиты

### 1. Почему новый тест в TDD сначала должен упасть?

Падение подтверждает, что тест действительно описывает ещё не реализованное поведение. Если тест сразу проходит, требование могло уже быть реализовано или тест может быть слишком слабым.

### 2. Чем Green отличается от окончательного качественного решения?

Green означает, что текущий тест и предыдущие тесты проходят. Код на этом этапе может быть минимальным и ещё нуждаться в улучшении структуры, имён и устранении дублирования.

### 3. Почему рефакторинг выполняется при зелёном наборе?

При зелёном наборе есть автоматическая проверка уже реализованного поведения. После структурных изменений можно сразу проверить, что наблюдаемое поведение не изменилось.

### 4. Что означает покрытие строк?

Это доля учитываемых строк программы, которые были выполнены во время запуска тестов.

### 5. Почему 100 процентов не доказывают отсутствие ошибок?

Потому что покрытие показывает выполнение кода, а не правильность ожиданий. Тест может выполнить строку, но не проверить результат, либо использовать недостаточный набор входных данных.

### 6. Какие тесты нужны для обеих ветвей is_full?

Нужны как минимум два сценария: курс не заполнен и курс заполнен. В данной работе дополнительно проверяется частично заполненное состояние.

### 7. Как покрытие помогает найти недостающий сценарий?

В отчёте видны невыполненные строки и частично пройденные ветви. Это позволяет сопоставить непокрытый участок с требованием и добавить тест, который проверяет реальное поведение.

> Примечание: журнал оформлен по последовательности требований из практической работы. В итоговом репозитории сохранены финальные тесты и реализация, а промежуточные состояния Red/Green не сохранялись отдельными коммитами.
